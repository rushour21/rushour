Building Rushour

Eight phases, thirty-eight stages. Each stage is one sitting's work with a test you can actually run; each phase ends at a gate that is passed by using the thing, not by finishing the code.

Two rules make this plan different from a task list. A stage is done when its check passes, not when the code is written — every row below names one. And a phase does not begin until the previous gate is passed by observed use, which is the same admission control the product imposes on its user. Building all eight phases back to back would reproduce exactly the failure the product exists to fix.

On the two newest additions

The dashboard and the streak both arrived after the spec was written, and both cut against something in it. That is fine, but worth being explicit about so the reasoning is not lost.

  • The dashboard softens "land on clock-in, never a dashboard". The resolution in 3.4: the day's state sits above the statistics, so Home answers "what now" before it answers "how am I doing".
  • The streak is on the kill list, and the objection stands — a broken streak becomes a reason to quit. Stage 3.5 keeps the pull and removes the trap: it counts showing up rather than perfection, and banks rest days so one missed day cannot zero it.
The discipline to keep. Every figure on the dashboard must still trace to something the user entered, and no badge may reward mere usage. The moment a number exists to be grown rather than to be read, this becomes the kind of app the whole thing was a reaction against.
